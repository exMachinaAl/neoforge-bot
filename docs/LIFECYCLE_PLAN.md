# docs/LIFECYCLE_PLAN.md - otak lifecycle: statistik -> task acak berbobot -> evaluasi -> upgrade -> tool tambahan (v1, 2026-10-12)
Status: RENCANA (belum ada kode). Melengkapi docs/ORCHESTRATOR_PLAN.md (L1..L4) dan docs/UI_PLAN_ADDENDUM_v1.2.md. Prinsip tetap: kontrak dulu (hanya menambah), otonomi bawaan MATI, killswitch menang, label status jujur, LLM hanya mengusulkan.

## 1. Gagasan inti
Siklus: **observe -> decide -> act -> evaluate -> learn**. Mesin utamanya DETERMINISTIK dan tidak butuh LLM (statistik + bobot persona + pengambil sampel berbiji). LLM adalah lapisan opsional: memberi peringkat ulang, menulis alasan, mengkritik hasil (saran), dan mengusulkan perubahan konfigurasi/tool. Alasan: murah, dapat diuji ulang (biji acak dicatat), tidak berhenti saat API mati, dan LLM tak bisa melanggar batas keselamatan karena filter keras ada di kode.

## 2. Komponen dan data
1. **Telemetri/Statistik** (`lifecycle/stats`): mencatat tiap task (skill, params ringkas, hasil, durasi) + SNAPSHOT KONTEKS saat mulai: jam Minecraft (tick, siang/senja/malam/fajar, hari ke-N), cuaca, jumlah pemain online, ancaman mob (jumlah/jarak/jenis hostile), HP/lapar, dimensi, stok inventory vs target, kematian terakhir. Agregat bergulir per (skill atau template) x (bucket konteks). Sumber data: tasks.log (hasil; konteks historis TIDAK ada), event bot.*, BotState. Setiap sinyal diaudit dulu (S-1): bot.players, bot.time, bot.isRaining/thunderState, entities sudah dipakai di kode; biome/cahaya/fase bulan = BELUM DIVERIFIKASI.
2. **Persona stats** (`lifecycle/persona`): kontrak Persona sudah ada (traits caution/aggression/curiosity/diligence/sociability, timing, chat, limits). Tambahan opsional (kontrak, commit terpisah): `needs` (energi/keamanan/kebosanan, 0..1), `affection`, `xp`, `level`. Persona mempengaruhi BOBOT, bukan kecerdasan. Perubahan trait dibatasi (+-0.02 per batch, dijepit 0..1, meluruh perlahan) dan tercatat.
3. **Cyclebook** (`lifecycle/cyclebook/*.json`): pustaka TEMPLATE task/batch: {id, skill atau makro, params dengan rentang, kategori (survive|gather|craft|social|explore|maintain), prasyarat (kapabilitas, stok, jam, dimensi), nilai dasar, pendinginan, estimasi durasi}. Dapat diperbarui tanpa rilis kode (lihat 6).
4. **Pembuat task acak berbobot** (`lifecycle/sampler`): memilih BATCH (1-5 task) dari cyclebook. Langkah: (a) FILTER KERAS (wajib 100%): HP>=batas, dimensi aman, antrean tidak dijeda, kapabilitas ada, bukan malam tanpa senjata untuk template berisiko, anggaran tak habis, template tidak dalam pendinginan; (b) SKOR tiap kandidat = kebutuhan x bobot persona x kecocokan konteks x peluang sukses (statistik) x (1 + bonus eksplorasi) x faktor keselamatan; (c) PILIH dengan softmax bersuhu T dan PRNG berbiji (biji + versi konfigurasi dicatat di batch -> dapat diputar ulang); (d) susun urutan (sleep sebelum dini hari, simpan sebelum tambang lagi, dll).
   Versi 1 sederhana: bobot tetap + epsilon-eksplorasi 10-20%. Versi 2: bandit (Thompson/UCB) per (template x bucket konteks) memakai statistik hasil. Jangan memulai dari versi 2.
5. **Batch** = kumpulan task bertujuan sama: {batchId, kategori, tasks[], konteks awal, biji, mode kebijakan, status proposed|approved|running|evaluated|archived}. Task membawa `batchId` (kontrak opsional). Engine tetap satu task per waktu; batch hanya pengelompokan dan evaluasi.
6. **Konfigurasi lifecycle yang bisa diperbarui**: cyclebook, bobot, rubrik skor, ambang upgrade, allowlist = berkas JSON bersertifikat skema, BERVERSI (lifecycle.version), muat-ulang panas, rollback satu langkah, log perubahan `lifecycle.log`. Usulan perubahan dari LLM berbentuk PATCH (JSON Patch) berstatus pending -> divalidasi skema + uji pada skenario -> disetujui pemilik -> diterapkan (versi naik). Tidak ada perubahan diam-diam.
7. **Evaluasi & skor** (`lifecycle/scorer`): skor batch 0..100 dari komponen OBJEKTIF: completion (rasio task OK), keselamatan (HP minimum, kematian, kerusakan diterima, item hilang), efisiensi (durasi vs estimasi), kecocokan konteks (apakah template layak untuk jam/ancaman/jumlah pemain saat itu), nilai (selisih stok vs tujuan), biaya (token). Awal (dapat diubah di konfigurasi): 0.35 completion, 0.20 keselamatan, 0.15 efisiensi, 0.15 kecocokan, 0.15 nilai, dikurangi penalti. MASUKAN MANUSIA: skor pemain 1-5 (UI) bobot 0.2 bila ada. EVALUASI AGEN (LLM, rubrik terstruktur): hanya SARAN, bobot maks 0.1 dan dijepit +-10 poin dari skor objektif; tidak pernah menaikkan komponen keselamatan. Skor dihitung dari log, bukan dari klaim agen (anti reward-hacking).
8. **Upgrade/progresi**: skor menggerakkan XP/level persona dan MEMBUKA kelayakan: batch lebih besar (1->3->5), allowlist lebih luas, kelayakan mode otonomi `auto-safe` (O-3), kelayakan promosi tool. Setiap kenaikan = KARTU USULAN di UI ("rata-rata 80 pada 10 batch tanpa pelanggaran: naik?") dan butuh persetujuan pemilik untuk tingkat otonomi/tool; perubahan trait persona kecil boleh otomatis dengan batas di atas. Penurunan otomatis bila ada pelanggaran keselamatan.
9. **Tool tambahan buatan agen** (fungsi vanilla hampir lengkap, jadi fokus pada komposisi). Tingkat risiko:
   - **T1 Makro deklaratif (mulai di sini)**: urutan skill yang sudah ada dengan parameter, kondisi, dan loop berbatas dalam JSON; dijalankan interpreter aman sebagai skill `macro.<nama>`. Divalidasi terhadap manifest; tanpa kode sembarang. Contoh: bangun-bed-lalu-tidur-lalu-ambil-bed, panen-tanam-simpan, patroli rute.
   - **T2 Template berparameter**: butir cyclebook (bukan kode).
   - **T3 Skill kode buatan model**: RISIKO TINGGI, bawaan TIDAK DIIZINKAN. Node `vm` bukan batas keamanan; sandbox kuat (isolated-vm dll.) berat di Termux. Bila suatu hari dipertimbangkan: hanya sebagai usulan berkas + tes di `tools/candidates/`, analisis statis (larang fs/child_process/net/require di luar daftar), tes mutasi lulus, diuji di server uji, ditinjau manusia -> status `reviewed` -> `approved` (keputusan pemilik di paket T-3).
   - **Registry tool**: manifest + asal (pemilik|agen, model, versi prompt, waktu, hash tes) + tingkat kepercayaan (candidate|reviewed|approved|disabled) + statistik pemakaian + batas anggaran. Otomatis diturunkan ke `disabled` bila gagal berulang. **Deteksi celah**: urutan task sukses yang berulang atau kegagalan berulang pada pola yang sama -> usulan makro (hanya usulan).
10. **Peran LLM** (setelah mesin deterministik terbukti): (a) peringkat ulang kandidat/menulis alasan; (b) evaluasi rubrik atas batch (saran); (c) mengusulkan PATCH konfigurasi dan makro; (d) menjawab tujuan bebas pemilik (Director sekarang). Semua keluaran divalidasi skema; tidak ada yang berjalan tanpa persetujuan/kebijakan.

## 4. Keselamatan (tidak bisa ditawar)
Filter keras sebelum pengambilan sampel; mode otonomi off|propose|auto-safe|auto (bawaan off); anggaran: panggilan/menit LLM, token/sesi, jumlah task/jam, batas operasi merusak (galian) per batch; killswitch menghentikan batch dan menjeda; audit `director.log` + `lifecycle.log` (biji, versi konfigurasi, keputusan, hasil); semua perubahan konfigurasi/tool berversi dan dapat dibatalkan; uji dulu di server uji; data pemain di prompt hanya jumlah (nama dilarang tanpa persetujuan); tool buatan agen tanpa akses jaringan/berkas.

## 5. Kontrak yang akan ditambah (hanya menambah, satu commit khusus per kelompok, diisi hanya bila kodenya ada)
Persona: needs, affection, xp, level. Task.batchId. Definisi baru: StatsSnapshot, Batch, BatchScore {total, komponen{...}, playerScore?, agentEval?}, LifecycleConfig {version, cyclebook[], weights, rubrik, ambang}, ToolManifest ekstensi {provenance, trust}. ## 6. Urutan eksekusi yang disarankan
Gelombang 1 (paralel, tanpa mengubah perilaku bot): A-1 kontrak | S-1 audit sinyal | S-2 pengumpul statistik (hanya menulis) | P-1 persona store + kartu UI baca-saja (usulan pemilik: persona stats dulu) | S-3 penghitung skor offline di tasks.log (dapat DIBUKTIKAN pada log nyata).
Gelombang 2: G-1 cyclebook + sampler MODE KERING (menghasilkan batch, tidak mengantre; bandingkan dengan aktivitas nyata) | U-1 kartu Batch/Skor | L-2 rubrik evaluator (saran) | T-1 spesifikasi makro.
Gelombang 3: G-2 mode propose + persetujuan (batch masuk antrean) | PR-1 progresi/upgrade | T-2 interpreter makro | L-1 peringkat ulang LLM.
Gelombang 4: C-1 konfigurasi berversi + patch | G-3 bandit | O-3 auto-safe (ORCHESTRATOR_PLAN) | T-3 keputusan kode buatan model (bawaan: tidak).
Jalur kritis: A-1 -> S-2 -> S-3 -> G-1 -> G-2 -> PR-1. Persona (P-1) dan UI (U-1) tidak menghalangi jalur kritis.
